## ENG-0001 evidence

Implemented test-first against
[ADR-0014](../decisions/ADR-0014-root-establishment-lineage.md) and its
[contract specification](../trust/root-establishment-lineage.md).

- `RootAuthorityLineage` carries no decision or approval fields — they are
  absent from the model, so no code path can populate one.
- `TrustLineage` is unchanged: both `TDEC` identifiers remain required.
- `declare_root_authority` persists one `root-establishment` lineage, reusing
  the already allocated `TLIN`. No `TDEC` is created; no second `TLIN` is
  allocated.
- `validate-store` reports an authority whose lineage is missing, of the wrong
  type, malformed in any stored value, or naming a different authority. It
  repairs nothing.
- Stored records are validated by reconstruction, not by field name, so a record
  whose keys are right and whose values are nonsense cannot satisfy the rule.
  Parse, type, and datetime failures become deterministic findings rather than
  crashes.

**Independently reviewed at `3b929cc`, then merged to `main` as `de6de9f` via
pull request #26 on 2026-08-04.** The review was conducted and attested
**outside GitHub**: pull request #26 carries no GitHub review record, no review
comment, and was merged by its author. Provenance for the independent review is
the operator's attestation, not a repository-native artefact — recorded here so
nobody later reads the exit gate as satisfied by evidence that does not exist.

**Released as `v0.9.7` on 2026-08-04.** The annotated, unsigned tag targets
`19ec85c` on `main`, and that released tree contains the reviewed implementation
`3b929cc`. No GitHub Release, release branch, release commit, or release PR was
created — the tag alone is the release, matching every prior version.

ENG-0001 has therefore satisfied its exit gate.

The existing production store is unchanged: `TLIN-000001` is **not** backfilled,
and `validate-store` reports its absence as an accurate finding. Releasing the
code fix does not retroactively create the record; the backfill remains a
separate, unauthorised action.

## ENG-0002 evidence

Implemented test-first against the
[post-root runtime sequence plan](../superpowers/plans/2026-08-03-post-root-runtime-sequence.md).

`validate-store` created the store it was asked to describe. Opening a store
initialised it, so validating an absent path built the store root, all six
record directories, `sequences/`, and `indexes/`, then reported the result
valid — a verdict partly describing the validator's own side effects.

- Opening for read is now separate from initialising. `ImmutableStore` gained
  `open_for_read()`, which constructs no directory and sets no mode; the
  initialising path is unchanged for every write command.
- `command_validate_store()` uses only that path. Exit codes are unchanged: `0`
  when valid, `1` when problems are reported, `2` for an invocation error.
- No filesystem mutation occurs whether the target is absent, empty, valid, or
  malformed, and repeated validation returns identical output over identical
  paths, modes, sizes, timestamps, and digests.

**Merged through pull request #28 as `4493cbc`, and released as `v0.9.8` on
2026-08-04.** The annotated, unsigned tag targets the release-record merge
commit on `main`, whose tree contains the independently reviewed implementation
`4af34a0`. As with `v0.9.7`, the tag alone is the release: no GitHub Release, no
release branch, no separate release commit.

Verdict and exit-code semantics are unchanged. `validate-store` still returns
`0` when valid, `1` when problems are reported, and `2` for an invocation error,
and an absent store still reports valid — pre-existing behaviour that ENG-0002
deliberately preserved rather than widened.

No production trust record was read, written, or repaired; `TLIN-000001` remains
un-backfilled, and validation still reports its absence as an accurate finding.
ENG-0002 performed no production repair or backfill of any kind.

The non-transactional write risk recorded under ENG-0001 is **unchanged and
still deferred**. ENG-0002 does not own it: an orphan root establishment lineage
is still undetected by the authority-to-lineage rule, and this change makes
validation read-only rather than adding the reverse check.

## ENG-0005 — Track A built, and it does not execute

**ENG-0005 Track A non-executing Capability Runtime foundation complete
locally; pending integration. The Track-B rootless execution prerequisite is
now provisioned and its sandbox proven, so real capability execution remains
blocked on one thing only: a separately authorised adapter implementation.**

Seven increments, each reviewed and accepted before the next was authorised,
plus two prerequisite corrections found by stopping rather than guessing.

| Increment | Delivers |
|---|---|
| A1 | immutable Capability Runtime store — its own root, identifiers, sequences, and lock |
| A2 | opaque invocation identity, canonical payload, and the binding digest that ties them to a decision |
| A3 | read-only verification of the selected Fabric evidence, through C8's inspection surface only |
| A4 | executable-package grammar, manifest schema v1, integrity verification, content-addressed staging |
| A5 | durable invocation decisions, exact replay, conflict, and refusal evidence |
| A6 | inspection, validation, and the governed interface that refuses |
| A7 | package-wide security guards and the composed non-execution proof |

Two prerequisites were corrected first, because A4 could not be built honestly
without them: the **executable package trust contract** (the manifest lives
beside the artefact it attests, so the approved artefact root is named as part
of the trusted computing base rather than the manifest being described as a
cryptographic root of trust), and a reviewed **descriptor-safe trusted-source
primitive** in `tools/common/`, since resolving a path and then opening it is a
race with whoever can write the directory.

**What it deliberately does not do.** There is no adapter, no subprocess, no
container, no shell, and no dynamic loading. `invoke` carries a governed
selection through binding, verification, staging, and durable evidence, and
then returns `no_authorised_adapter`. The durable record says
`execution-prepared`, because the preparation succeeded; what is unavailable is
a separately authorised execution mechanism. **The absence of a next step is a
tested property**, asserted over every production module by discovery rather
than by a maintained list.

**Fabric remains the selection and governance authority.** The Capability
Runtime verifies the decision the Fabric already made and cannot select,
re-select, rank, or substitute anything.

**Track B is provisioned, and it still does not execute anything.** On
2026-08-11 the `schai` host received the rootless prerequisite set — podman
4.9.3, the `kyri-capability` account, its subuid/subgid ranges, lingering, a
rootless graphroot, and one digest-pinned image — and an enforcement battery
proved the sandbox across eighteen isolation domains: rootless identity
mapping, network denial, filesystem denial, read-only rootfs, read-only input
mount, capability and privilege profile, device and GPU denial, memory, CPU,
PIDs, environment isolation, lifecycle capture, and canonical-staging denial.
No sysctl and no AppArmor policy changed;
`apparmor_restrict_unprivileged_userns` remains `1`. Rootful `podman.socket`
and `podman.service` are masked and inactive.

**A provisioned sandbox is not an adapter.** There is still no subprocess, no
container invocation, and no execution path in `tools/capability/`, so `invoke`
continues to return `no_authorised_adapter`. What the host can now do is run
isolated synthetic rootless containers; what the Capability Runtime can do is
unchanged. **ENG-0005 is not complete.** The next step is a first-adapter
specification, which is authorised to be written and not to be implemented.

Two corrections came out of the battery rather than out of review. The
PID-limit probe was **inconclusive** on its first run because it exhausted the
PID budget and then needed a fork to report its own diagnostics; a corrected
probe read the cgroup leaf from the host and closed the gate on `pids.peak=64`
and `pids.events: max 1`. And the execution identity could read
`/opt/schott-platform`, because the directory was mode `0755` — world traverse,
not a group or ACL grant. It is now `0750 cschott:cschott`, because the
two-identity model requires the execution identity to lack repository access in
its own right rather than relying on an adapter's promise never to run
capability code outside a container.

Four findings are recorded as normative inputs to the first-adapter
specification in [§23 of the rootless execution
prerequisite](../superpowers/plans/2026-08-10-rootless-execution-prerequisite.md):
container output is hostile filesystem input to the coordinator; lifecycle
state precedes `ExitCode`; canonical staging requires a per-invocation handoff;
and disk exhaustion is unbounded because `/data` is mounted `noquota`.

ENG-0006 has not begun, no subjects have been seeded, and no TrustGateway
cutover has been performed.

### Deferred items carried forward

- **Deferred D — persistence-plane root permission hardening.** Both the Fabric
  and Capability Runtime stores leave the store root at the ambient umask while
  creating `0700` directories inside it. Matching the released behaviour was
  deliberate: changing one plane alone would give two planes different root
  semantics. A cross-plane ruling should cover the Fabric, Capability, and
  Trust roots, ownership and group, fresh-store versus existing-store, and
  `0700` against `0750`.
- **Deferred E — shared persistence path/ownership guard evaluation.**
  Containment moved to `tools/common/containment.py`, and descriptor-safe
  opening to `tools/common/trusted_source.py`. Whether ownership validation,
  unresolved-link rejection, and regular-file validation are one primitive or
  several is still open, and merging them by assumption is how a security
  helper acquires a shape nobody chose.
- **Deferred F — governed package-content integrity.** The current model is a
  trusted artefact repository, a closed manifest, digest verification, and
  content-addressed staging. **The manifest does not independently prove the
  bytes were the ones originally admitted**; future work should evaluate
  binding package content authenticity into immutable governed evidence.
- **Deferred G — execution-identity visibility of coordinator data roots.** Six
  coordinator-owned directories under `/data/kyri` — `artifacts`, `backups`,
  `datasets`, `exports`, `scratch`, and `work` — are mode `0755` and therefore
  readable by the execution identity, through the same world-traverse mechanism
  that was corrected on the repository. They are not a Track-B sandbox gate:
  none is mounted into a container, all are currently empty, and the specific
  repository contract violation was corrected separately. **`0755` is not
  thereby established as acceptable long-term**; the review should determine
  each directory's intended consumers before any mode is changed, so the fix
  does not break a consumer nobody enumerated.

## Capability Runtime is part of Fabric delivery

**ENG-0005 is an increment of the Fabric, not a separate plane.** ADR-0012
defines capability definitions, instances, packages, routes, and selection as
Fabric entities; executing them is the part of the Fabric that actually runs
work. ENG-0005 is therefore sequenced inside Fabric delivery — after the Fabric
engine exists (ENG-0004) and before Health has anything worth observing
(ENG-0006).

It remains a distinct ledger entry because it needs its own accepted
specification and its own review boundary — not because it is optional or
indefinitely deferred. **Its exact boundary against ENG-0004 is not yet
specified** and must be settled by that specification before implementation
begins.

## Two gates, not one

**TrustGateway cutover is intentionally not the Fabric Runtime gate.** The
Operator Root ceremony was.

**Fabric Runtime entry gate:** Operator Root ceremony complete -> ENG-0001
released -> ENG-0002 released.

**TrustGateway production cutover gate:** Fabric Runtime validated -> Health
Runtime validated -> initial subjects seeded -> verdict source ready -> rollback
validated -> deployment evidence retained -> TrustGateway cutover.

Cutover remains last so the runtimes can exist, be validated, and have their
subjects seeded before production traffic depends on them.

and [ADR-0014](../decisions/ADR-0014-root-establishment-lineage.md).
