## ENG-0001 evidence

Implemented test-first against
[ADR-0014](../decisions/ADR-0014-root-establishment-lineage.md) and its
[contract specification](../trust/root-establishment-lineage.md).

- `RootAuthorityLineage` carries no decision or approval fields — they are
  absent from the model, so no code path can populate one.
- `TrustLineage` is unchanged: both `TDEC` identifiers remain required.
- `declare_root_authority` persists one `root-establishment` lineage, reusing
  the already allocated `TLIN`. No `TDEC` is created; no second `TLIN` is
  allocated.
- `validate-store` reports an authority whose lineage is missing, of the wrong
  type, malformed in any stored value, or naming a different authority. It
  repairs nothing.
- Stored records are validated by reconstruction, not by field name, so a record
  whose keys are right and whose values are nonsense cannot satisfy the rule.
  Parse, type, and datetime failures become deterministic findings rather than
  crashes.

**Independently reviewed at `3b929cc`, then merged to `main` as `de6de9f` via
pull request #26 on 2026-08-04.** The review was conducted and attested
**outside GitHub**: pull request #26 carries no GitHub review record, no review
comment, and was merged by its author. Provenance for the independent review is
the operator's attestation, not a repository-native artefact — recorded here so
nobody later reads the exit gate as satisfied by evidence that does not exist.

**Released as `v0.9.7` on 2026-08-04.** The annotated, unsigned tag targets
`19ec85c` on `main`, and that released tree contains the reviewed implementation
`3b929cc`. No GitHub Release, release branch, release commit, or release PR was
created — the tag alone is the release, matching every prior version.

ENG-0001 has therefore satisfied its exit gate.

The existing production store is unchanged: `TLIN-000001` is **not** backfilled,
and `validate-store` reports its absence as an accurate finding. Releasing the
code fix does not retroactively create the record; the backfill remains a
separate, unauthorised action.

## ENG-0002 evidence

Implemented test-first against the
[post-root runtime sequence plan](../superpowers/plans/2026-08-03-post-root-runtime-sequence.md).

`validate-store` created the store it was asked to describe. Opening a store
initialised it, so validating an absent path built the store root, all six
record directories, `sequences/`, and `indexes/`, then reported the result
valid — a verdict partly describing the validator's own side effects.

- Opening for read is now separate from initialising. `ImmutableStore` gained
  `open_for_read()`, which constructs no directory and sets no mode; the
  initialising path is unchanged for every write command.
- `command_validate_store()` uses only that path. Exit codes are unchanged: `0`
  when valid, `1` when problems are reported, `2` for an invocation error.
- No filesystem mutation occurs whether the target is absent, empty, valid, or
  malformed, and repeated validation returns identical output over identical
  paths, modes, sizes, timestamps, and digests.

**Merged through pull request #28 as `4493cbc`, and released as `v0.9.8` on
2026-08-04.** The annotated, unsigned tag targets the release-record merge
commit on `main`, whose tree contains the independently reviewed implementation
`4af34a0`. As with `v0.9.7`, the tag alone is the release: no GitHub Release, no
release branch, no separate release commit.

Verdict and exit-code semantics are unchanged. `validate-store` still returns
`0` when valid, `1` when problems are reported, and `2` for an invocation error,
and an absent store still reports valid — pre-existing behaviour that ENG-0002
deliberately preserved rather than widened.

No production trust record was read, written, or repaired; `TLIN-000001` remains
un-backfilled, and validation still reports its absence as an accurate finding.
ENG-0002 performed no production repair or backfill of any kind.

The non-transactional write risk recorded under ENG-0001 is **unchanged and
still deferred**. ENG-0002 does not own it: an orphan root establishment lineage
is still undetected by the authority-to-lineage rule, and this change makes
validation read-only rather than adding the reverse check.

## The defect sprint is complete; ENG-0003 has not started

Both released defects are now merged and released — ENG-0001 as `v0.9.7` and
ENG-0002 as `v0.9.8` — so the Fabric Runtime entry gate conditions are met.

**ENG-0004 has since been delivered and released as `v0.9.9`; nothing after it
has begun.** ENG-0005 Capability Runtime, ENG-0006 Health Runtime, and ENG-0003
TrustGateway cutover remain unstarted and unauthorised. A satisfied entry gate
is permission to *specify* the next increment, not to implement it: each still
requires its own accepted specification, test-first plan, review, and release
boundary before any code is written.

## Capability Runtime is part of Fabric delivery

**ENG-0005 is an increment of the Fabric, not a separate plane.** ADR-0012
defines capability definitions, instances, packages, routes, and selection as
Fabric entities; executing them is the part of the Fabric that actually runs
work. ENG-0005 is therefore sequenced inside Fabric delivery — after the Fabric
engine exists (ENG-0004) and before Health has anything worth observing
(ENG-0006).

It remains a distinct ledger entry because it needs its own accepted
specification and its own review boundary — not because it is optional or
indefinitely deferred. **Its exact boundary against ENG-0004 is not yet
specified** and must be settled by that specification before implementation
begins.

## Two gates, not one

**TrustGateway cutover is intentionally not the Fabric Runtime gate.** The
Operator Root ceremony was.

**Fabric Runtime entry gate:** Operator Root ceremony complete -> ENG-0001
released -> ENG-0002 released.

**TrustGateway production cutover gate:** Fabric Runtime validated -> Health
Runtime validated -> initial subjects seeded -> verdict source ready -> rollback
validated -> deployment evidence retained -> TrustGateway cutover.

Cutover remains last so the runtimes can exist, be validated, and have their
subjects seeded before production traffic depends on them.

See [0002 - Runtime Sequencing Correction](0002-runtime-sequencing-correction.md)
and [ADR-0014](../decisions/ADR-0014-root-establishment-lineage.md).
